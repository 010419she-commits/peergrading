# 在现有仓库中进行双 Agent 协作

本地桌面可以直接使用仓库协作，不需要 PeerGrading 登录、会员或设备授权。作者读取仓库后编辑文件，审查者读取同一工作目录与每轮差异；需要继续修改时，两位 Agent 交换角色。普通「生成文字 / 代码成果」方式仍然保留。

## 开始使用

1. 安装 Git，并安装、登录 Kimi Code、Codex 或 Claude Code CLI。两位都必须选择这三类 CLI 中的一种；可以选同一种工具但使用不同人设。纯 API 模型和剪贴板中转不支持直接编辑仓库。
2. 在原仓库提交已有改动，或自行保存这些改动。仓库至少需要一个提交；未提交和未跟踪文件会阻止启动。程序不会清理、重置或覆盖它们。
3. 打开本地桌面工作台，选择「修改现有 Git 仓库」，选择目录并点「检查仓库」。开发者可通过 `npm run dev` 在本机工作台输入绝对路径。公网下载站点不会接受服务器仓库路径。
4. 描述任务，选择 A、B，可填写每行一条的验证命令，例如 `npm test`、`npm run build`、`python3 -m unittest`、`cargo test`。命令按参数数组执行，支持引号包围含空格的参数，不支持管道、重定向、变量展开或多条命令用 `&&` 拼接。Windows 路径建议用正斜杠并为含空格的路径加引号。
5. 点击开始。任务从原仓库 HEAD 创建独立工作目录与 `codex/peergrading-*` 分支。界面显示讨论、每轮版本、验证结果和可下载的 Git 补丁。仓库自身的 AGENTS.md 等说明仍由相应 CLI 读取。

## 工作目录与验证

隔离目录和清单位于本次会话的 `repository/` 下，清单包含源仓库、任务分支、工作目录、各轮提交和验证结果。源码在这个目录中真实修改，每一版有对应 Git 提交和补丁；目录不会在任务结束时删除。单个仓库同时只允许一个协作任务。审查和讨论阶段使用只读权限，发现意外改动会终止并保留现场。

验证命令在工作目录中运行，不使用操作系统容器隔离；仅运行你信任的项目。工作目录只包含已提交文件，不会复制原目录里的 `.env`、忽略文件或 `node_modules`。依赖、环境变量和凭证需要你按项目要求准备，可以将安装命令作为第一条验证命令，例如 `npm ci`。每条命令默认最多运行两分钟。未配置测试时，只能说明模型审查通过，不代表执行验证通过。

每条校验记录包含独立 ID、起止时间、退出码及执行前后的 Git 文件树。整批检查与最后提交必须对应同一文件树：若安装、格式化、生成文件或其他验证命令修改了已跟踪或未忽略的交付文件，本轮检查全部失效，即使退出码是 0 也不能批准；应由下一轮在稳定的文件上重新运行。Git 忽略的缓存和依赖不计入文件树。这个关联不验证外部服务、环境或测试期间修改后恢复的文件，也不能证明测试覆盖充分。

大日志保留 stdout、stderr 各自末尾最多 200,000 字符，并在界面标记截断；不会因为测试输出较多而终止正常命令。超时、取消和非零退出码仍按真实结果处理。Git 差异等需要完整输出的操作保留严格大小限制。

审查者必须在最后一行单独写 `VERDICT: APPROVE` 或 `【结论】通过` 才能批准；代码围栏、引用及未闭合的 HTML 示例中的标记无效。每次审查和讨论后的复审都会保存结论、审查者、版本、提交及检查 ID，旧版本的通过不能用于新版本。未配置检查时，界面会明确提示没有执行自动验证。

Git worktree 用于隔离文件和分支改动，并非进程安全沙箱。Claude 作者允许文件读取和编辑，测试由程序运行；Codex 使用其工作目录写入沙箱。Kimi Code 使用专用文件工具列表，审查阶段仅开放读取；独立启动配置不加载原有命令钩子或 MCP。两位 Agent 不会被要求推送、自动合并或删除原目录。子模块、Git LFS、特殊 Git 过滤器及需要外部服务的仓库可能需要额外准备；无法保证任意语言、任意构建环境无需配置即可运行。

## 并行预审与缓存的正确性

加速任务必须绑定完整快照，不直接写当前工作区。结果只有在当前内容的 SHA-256 与来源快照一致时才能采纳；摘要不匹配、任务取消或验证失败时，陈旧结果必须丢弃或回退，不能标记为新版本已通过。

精确缓存只在快照及全部有效审查输入一致时复用。缓存命中不能跳过测试或审查结论检查，也不能把旧版本批准转移到新版本。通用 Chat API 不提供可移植的跨请求 token/KV 共享计算接口，详见 [加速算法与 API 边界](acceleration.md)。

## 取回成果

结束后在右侧查看任务分支和目录，打开每一版补丁审阅。确认满意后，在原仓库执行 `git merge <界面显示的任务分支>`。若只要部分提交，可自行 cherry-pick 或应用补丁。合并前正常处理本地新改动与冲突；程序不会自动替你处理原目录冲突。

停止、失败或达到轮数上限时都会保留任务工作目录与已完成提交，界面区分已通过、达到上限、已取消和失败。最大轮数后的版本不会未经审查就被标成成功。测试失败不能被 Agent 的「通过」结论覆盖。

会话在运行开始前即写入历史，随后持续保存消息和版本；停止或异常退出后可从历史查看已经保存的成果。服务重启后，未正常结束的会话显示「已中断」。这只恢复查看，不会自动重新启动 Agent 或继续修改仓库。正常停止、执行失败也保留已完成的版本；旧格式会话仍可读取。

每个会话的精简事件历史上限为 8 MiB、8,192 条事件（逐 token 消息合并存储，进度跳动不留存），另保留少量结束记录空间。达到上限会停止任务并保留此前成果。持续日志约每 256 KiB 或重要事件生成原子检查点；进程强制退出时忽略未写完整的最后一条日志，中间损坏则报错。配置存档只保存展示所需字段，不保存 Agent runner 和媒体 provider 的密钥。

任务目录无需保留后，可按 Git 正常流程执行 `git worktree remove <任务目录>`，再自行删除对应任务分支。仍有未提交工作时应先检查和保存，避免使用强制删除。

## 开发验证

运行 `npm test` 验证临时仓库中的角色轮换、真实写文件、原目录隔离、取消、失败、快照采纳和精确缓存等行为；测试默认不调用真实付费模型。`npm run bundle` 同时生成 `dist/server.mjs`、`dist/site-server.mjs` 与 `public/app-vendor.js`。真实 CLI 授权、模型权限和多系统安装仍须在各自环境完成。
