# 加速算法与通用 Chat API 边界

加速的目标是减少串行等待和完全相同的重复审查，而不是减少必要的审查或放松通过条件。核心组合是：**完整快照并行预审 + SHA-256 采纳/回退 + 精确缓存**。

## 1. 完整快照

每个预审任务必须绑定一份完整、可重读输入快照，而不是依赖“工作区大概没变”或若干增量片段。快照需要覆盖会影响结果的内容与审查上下文，并具有稳定标识。

- 预审只能读取其绑定快照，不直接修改当前工作区。
- 输出记录所依据的快照摘要；没有摘要的结果不能作为当前版本结论。
- 快照让并行任务获得一致输入，也便于在失败、取消或版本前进时明确丢弃陈旧结果。

完整快照是正确性边界，不表示每次都重复传输全部仓库，也不承诺模型供应商会缓存这些内容。

## 2. 并行预审与 SHA-256 采纳/回退

相互独立的预审可以在后台并行执行；需要结论时，只采纳仍与当前状态匹配的结果。

```text
生成完整快照 S，并计算 SHA-256 = H
        │
        ├─ 并行预审 A(S)
        └─ 并行预审 B(S)（若存在独立任务）
        │
准备采纳时重新计算当前快照摘要 H′
        │
        ├─ H′ = H：结果仍对应当前输入，可按正常审查流程采纳
        └─ H′ ≠ H：结果已陈旧，丢弃候选或回退到已知快照，再基于新快照计算
```

SHA-256 在这里用于识别内容版本和发现陈旧结果，不是身份签名。摘要不匹配时禁止把旧结论、旧补丁或旧缓存标记为新版本已通过；取消、失败和超时也沿用同一规则。采纳预审结果仍不能跳过测试、审查结论解析或仓库验证。

## 3. 精确缓存

缓存键必须由完整有效输入计算，包括快照内容以及实际影响输出的模型、角色和审查上下文。任何有效输入变化都产生不同键。

- 命中条件是完全相同的键和完整性校验，不使用文件名、修改时间、相似文本或“同一轮次”代替内容。
- 缓存结果仍带有原始快照摘要，复用前再次核对当前摘要。
- 缓存不跨版本猜测，不把旧版本批准转移到新版本，不保存不必要的密钥。
- 清空缓存只影响速度，不应改变最终审查结果。

## 4. 通用 Chat API 不能承诺 token 级共享计算

常见 `chat/completions` 风格 API 只提供请求、响应和可选的 token 流。它没有跨供应商、跨独立请求的可移植接口，让应用直接共享 KV cache、注意力状态或逐 token 中间计算。

因此：

- 两个并行请求即使拥有相同前缀，也不能据此宣称只计算了一次前缀。
- 流式输出是传输方式，不等于共享计算。
- 某些供应商可能提供自动提示缓存、显式上下文缓存或批处理；其命中条件、计费、保留时间和隔离规则是供应商特定能力，不能由通用 Chat API 推断。
- PeerGrading 的快照复用和精确缓存位于应用层，不能宣传为保证发生的模型内部 token/KV 共享。

只有在所选供应商明确提供并已实际启用相应能力时，才能按该供应商文档描述其缓存；应用自身仍须遵守快照摘要和精确缓存规则。

## 5. 验证重点

涉及加速的修改至少应覆盖：相同快照可复用、内容变化必失配、模型或审查上下文变化不误命中、并行完成顺序不影响结论、陈旧结果被拒绝、取消与异常不污染缓存，以及缓存开关前后最终交付一致。性能提升应单独测量，不用减少测试或审查次数来制造“加速”。
